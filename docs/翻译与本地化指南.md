# 翻译与本地化指南

> 项目用 Cocos Creator 官方本地化插件（localization-editor）做中英双语。本文记录体系结构、工作流和踩过的坑。

## 一、体系结构

| 层 | 位置 | 说明 |
|---|---|---|
| 词条数据 | `assets/翻译/zh-Hans-CN.xlsx`、`en-US.xlsx` | 三列：`key / sourceValue / targetValue`（sourceValue = 中文原文，targetValue = 该语言的显示值） |
| 代码入口 | `assets/scripts/配置/翻译Key.ts` | 静态常量类，每个词条一个 `static 属性 = 'Key'`，注释里保留原中文串 |
| 运行时 API | `l10n.t()` | 插件提供的查询函数，翻译Key 封装了三种用法（见下） |

**静态 Label**：直接给节点挂官方 `L10nLabel` 组件，不写代码。
**RichText/动态文本**：代码里用翻译Key 强行赋值（官方组件不支持 RichText）。

## 二、代码中的三种用法（翻译Key.ts）

```ts
翻译Key.翻译(翻译Key.攻击)                          // 单词条
翻译Key.翻译格式化(翻译Key.等级格式, 等级)           // 格式化: 'LevelFormat' = '{0}级' / 'Lv.{0}'
翻译Key.属性名称翻译(属性)                           // 按枚举拼 key: 'AttrName_' + 属性类型
```

- `翻译格式化` 把 `{0}` `{1}` 占位符替换为参数（实现在翻译Key.ts:25，用 `str.replace(/{(\d+)}/g)`）
- `翻译Key.Is英语()` 可按语言分支（极少需要，优先用格式化词条让两种语言各写整句）
- key 命名两种风格并存：拼音 key（`DuoWanJiaHunZhan` 多玩家混战）和英文语义 key（`LevelFormat`、`AttrName_3`、`ProjectileFireCount`）。新词条建议用**英文语义 key**，属性类枚举词条统一 `AttrName_数字`

## 三、加新词条的完整步骤（缺一不可）

1. 两个 xlsx 各插入一行（`key / sourceValue(中文) / targetValue`），中文表和英文表的行顺序无需一致
2. `翻译Key.ts` 加 `static 常量名 = 'Key'`，注释写原中文
3. 调用点改用 `翻译Key.翻译格式化(...)`
4. **编辑器"面板=>本地化编辑器"里重新导入 xlsx**（xlsx 是源，不导入不生效）

## 四、核心规则（踩坑总结）

### 1. 禁止在字符串拼接里硬编码任何语言文字

❌ 反例（BattleUI.ts 修复前）：
```ts
str详情 += 翻译Key.属性名称翻译(属性) + ':' + 等级 + '级\n'   // 英文环境显示 "Rocket:3级"
```

✅ 正确：整句进格式化词条，`{0}`/`{1}` 占位：
```ts
str详情 += 翻译Key.翻译格式化(翻译Key.属性等级格式, 翻译Key.属性名称翻译(属性), 等级) + '\n'
```
`AttrLevelFormat`：中文 `{0}:{1}级`，英文 `{0}: Lv.{1}`

### 2. 中英文语序可能不同，格式化词条必须包含整句结构

中文 `N级` 是后缀，英文 `Lv.N` 是前缀——只把"级"字做成词条解决不了语序问题。凡是"属性名 + 数字 + 单位"这类组合，一律整句格式化，单位（级/毫秒/米）也要进占位符或整句里。

### 3. 标点也是语言的一部分

冒号、括号、换行后的标点写进 targetValue，不要在代码里拼 `':'`。

## 六、中英词条一致性质检（2026-11 案例）

**脚本：`.codebuddy/skills/client-translation/scripts/check_translation_gaps.py`**（跑一次即可得三份报告），检查三类问题：

1. **key 缺失**：`中文key集合 - 英文key集合`。英文缺 key 时 L10nLabel/代码会回落显示中文原文，英文环境直接破功
2. **未翻译行**：英文表 `targetValue == sourceValue`（还是中文）。注意 target 等于中文有两种情况：故意不翻的专有名词、以及真的漏翻，需要人工分辨
3. **多出的 key**：往往是 key 写错的产物

### 关键教训：key 的引用可能在 prefab 里，不在代码里

检查"缺的 key 到底在不在用"时，**只搜 .ts 会漏报**——L10nLabel 组件挂在 prefab/scene 上，key 存在节点序列化数据里。正确做法是全搜 `.ts + .prefab + .scene + .mtl`。案例：英文缺的 10 个 key 里，4 个（`KeyJiJia`/`QueDing`/`RotateCamera`/`XiangQingQu`）挂在 `battleUI.prefab` 上实际在用，其余 6 个是无引用死键（保留未删）。

### 顺手能发现的问题

- **key 名带中文**：英文表曾出现 `Key机甲`（应为 `KeyJiJia`），表现为"缺一个 key + 多一个 key"同时出现——遇到这种不对称先怀疑改名事故
- **重复行**：同一 key 两行（旧行中文目标 + 新补英文行），补翻前先查目标 key 是否已存在，补完必须复检 0 缺失 0 未翻译
- **sourceValue 本身是英文的行**（如 `XiangQingQuXiaoDianJiDiMian`）：说明当初录入时 source 就是英文，翻译时 target 照抄即可
